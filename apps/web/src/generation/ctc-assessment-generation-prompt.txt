## OUTPUT CONTRACT

Return valid JSON only.

Do not use Markdown, commentary, explanations, or code fences outside the JSON document.

The document must contain:

- `"schemaVersion": "1.0"`
- `"preset": "ctc"` inside the assessment object
- `"durationSeconds": 10800`
- exactly three single-function problems
- slots exactly 1, 2, and 3
- problem IDs exactly `"p1"`, `"p2"`, and `"p3"`
- every function named `"solution"`

Design the three problems as one coherent 180-minute software-engineering coding assessment. The assessment should feel implementation-heavy and logic-heavy rather than like a competitive-programming contest.

Target a prepared candidate to need approximately:

- Q1: 25–35 minutes
- Q2: 35–45 minutes
- Q3: 45–60 minutes

The candidate should have meaningful time remaining for testing and debugging. Keep the UTF-8 JSON comfortably below the repository's assessment import size limit. Do not add properties outside the supported assessment schema.

## SUPPORTED TYPES

Use only these TypeSpec forms:

- `{"kind":"int"}`
- `{"kind":"long"}`
- `{"kind":"boolean"}`
- `{"kind":"string"}`
- `{"kind":"array","items":TypeSpec}`

Arrays may recursively contain another supported TypeSpec.

Do not use objects, maps as parameter types, tuples, floating-point types, nullable types, custom classes, trees, or linked-list node objects. Represent structured input with parallel arrays, arrays of strings, nested arrays, or other supported shapes.

Every test argument list must exactly match the function signature. Every expected result must exactly match the declared return TypeSpec. Names must be portable Java/C++/Python identifiers, must not be reserved words, and parameter names must be unique within each signature. All integer JSON literals must be JSON safe integers.

## TARGET CTC SWE STYLE

Generate three substantial software-engineering coding tasks. The core challenge should usually come from:

- understanding a precise specification;
- translating rules into reliable code;
- maintaining state correctly;
- choosing ordinary data structures well;
- handling operation ordering;
- avoiding indexing and boundary mistakes;
- recognizing a reasonable scalability requirement;
- testing edge cases.

Strongly favor combinations of arrays, strings, hash maps, hash sets, counters and frequency state, sorting, stacks, queues or deques, parsing and tokenization, state machines, sequential simulation, event processing, prefix or running aggregates, two pointers, sliding windows, straightforward greedy reasoning, and practical indexing or interval logic.

Occasionally use BFS, DFS, binary search, a heap or priority queue, interval processing, or simple dynamic programming when it naturally fits.

Do not make the assessment depend on segment trees, Fenwick trees, suffix arrays, suffix automata, advanced graph algorithms, max flow, computational geometry, difficult combinatorial dynamic programming, obscure number theory, or specialized contest tricks.

Do not test finance knowledge, trading knowledge, probability puzzles, market microstructure, mental math, or brainteasers. Neutral software, systems, operations, records, scheduling, text-processing, or data-processing scenarios are appropriate.

## QUESTION 1 PROFILE

Q1 must be a direct but non-trivial implementation problem at Medium difficulty, calibrated for approximately 25–35 minutes.

It should be understandable within a few minutes, require multiple implementation steps, reward clean decomposition and ordinary data structures, and contain several meaningful edge cases. It must not be trivial boilerplate, a five-minute warm-up, or depend on an obscure insight.

## QUESTION 2 PROFILE

Q2 must emphasize stateful logic or specification fidelity at Medium difficulty, calibrated for approximately 35–45 minutes.

Favor evolving state, commands, records, events, transformations, ordering-sensitive rules, and careful bookkeeping with maps, sets, stacks, queues, counters, parsing, or related ordinary structures. Hidden tests should expose incorrect assumptions without relying on ambiguous wording.

## QUESTION 3 PROFILE

Q3 must be performance-aware while remaining implementation-centered, at Medium to upper-Medium difficulty, calibrated for approximately 45–60 minutes.

Include one meaningful scalability observation. An obvious repeated-scan or naive quadratic approach should fail the largest intended tests. The intended solution must use a conventional technique derivable from the constraints, such as hashing, prefix state, sorting plus scanning, a heap, two pointers, a sliding window, monotonic processing, interval processing, or binary search. Do not turn Q3 into a Hard-LeetCode-style trick problem.

## PROBLEM DIVERSITY

The three problems must have meaningfully different mechanics. Do not generate three array scans, three matrix/grid problems, three command simulators, three problems using the same central data structure, two reskins of the same algorithm, or renamed copies of well-known questions.

Internally compare the three concepts before emitting JSON. If two are substantially similar, replace one. Do not force a finance or trading theme.

## DESCRIPTION QUALITY

Each description must state the task completely, define terminology before use, specify indexing conventions, operation ordering, tie-breaking, boundaries, inclusive/exclusive ranges, and valid-input guarantees where applicable. Difficulty must come from implementation and reasoning, not ambiguity.

## CONSTRAINTS AND COMPLEXITY

Give explicit numeric constraints for every parameter and nested collection where relevant. Constraints must agree with the reference solution, intended complexity, test data, and Java/C++/Python execution limits.

At least one problem, preferably Q3, must have constraints large enough that a clearly naive implementation fails performance-oriented hidden tests. Prefer recognizable complexities such as O(n), O(n log n), O(n + m), or O((n + q) log n). Do not require an obscure data structure merely to satisfy the limits.

If intermediate calculations can exceed 32-bit signed range, say so through the constraints and use the `long` TypeSpec when the returned value requires it.

## EXAMPLES

Provide 2–4 meaningful examples per problem. Examples must be small enough to understand, demonstrate normal behavior, clarify an important rule or edge condition, and contain correct outputs.

## TESTS

Provide 2–4 visible tests per problem. Visible tests should support understanding and basic debugging rather than exhaustively reveal the solution.

Target approximately 12–18 hidden tests per problem while keeping the full JSON reasonably sized. Cover applicable cases such as minimum sizes, single-element inputs, empty collections when allowed, duplicates, equal/distinct values, ties, first and last positions, repeated operations, state transitions and resets, unusual valid ordering, zeros, negatives when permitted, large values, overflow boundaries, off-by-one transitions, adversarial ordering, and performance stress.

Do not add invalid inputs unless the task explicitly requires handling them. Do not label tests with hints that reveal the solution. Hidden stress data must be concrete JSON, meaningful, and large enough to distinguish clearly naive solutions without making the import unwieldy.

## REFERENCE SOLUTIONS

For every problem:

- `validation.referenceLanguage` must be `"python"`;
- `validation.referenceSolution` must define `solution(...)`;
- the implementation must be deterministic, efficient, and obey the signature;
- it must handle all stated constraints and return the declared TypeSpec;
- it must not read stdin, print output, use randomness, access the network/filesystem/environment/processes, or depend on third-party libraries.

The reference solution is validation infrastructure, not candidate-facing explanation. Use ordinary Python language and standard-library features compatible with the practice tool.
