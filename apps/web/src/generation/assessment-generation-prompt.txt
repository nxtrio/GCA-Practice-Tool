Create one original, internally consistent practice assessment modeled on the structure and skill profile of the CodeSignal General Coding Assessment (GCA).

The goal is to reproduce the **style, pacing, implementation demands, constraint reasoning, and difficulty distribution** of a GCA without copying or closely paraphrasing any real, proprietary, leaked, or previously used CodeSignal problem.

# GCA REALISM REQUIREMENTS

Design the four problems as **one coherent 70-minute assessment**, not four unrelated LeetCode-style difficulty labels.

Difficulty refers to difficulty **under a shared 70-minute assessment clock**.

Questions should be concise enough to understand quickly, but contain enough edge conditions to reward careful implementation.

Favor ordinary programming constructs and broadly available standard-library data structures.

The assessment should be language-agnostic and equally reasonable to solve in Java, C++, or Python.

Do not require obscure mathematical facts, specialized competitive-programming algorithms, advanced graph algorithms, advanced dynamic programming, segment trees, Fenwick trees, tries, suffix structures, computational geometry, or other niche techniques unless explicitly requested by the user.

The challenge should come primarily from:

* translating rules into correct code;
* handling boundaries and edge cases;
* recognizing useful representations;
* using common data structures;
* understanding constraints;
* replacing an obviously too-slow approach when necessary.

Do not deliberately hide crucial behavior behind ambiguous wording.

A strong candidate should lose time because of reasoning or implementation difficulty, **not because the specification is unclear**.

# SLOT PROFILE

## Slot 1 — Fundamental implementation

Target solve time: approximately **5–10 minutes**.

Typical skills:

* array traversal;
* string traversal;
* simple transformations;
* conditionals;
* counting;
* neighboring elements;
* straightforward aggregation;
* simple indexing and boundaries.

Characteristics:

* The intended idea should be apparent quickly.
* The main risk should be implementation or boundary mistakes.
* Normally requires only one traversal or a few simple loops.
* Avoid requiring a clever algorithmic observation.
* Prefer O(n), O(n·k) for very small k, or another obviously adequate complexity.
* Include at least one boundary condition that a careless implementation could mishandle.

Do not make Slot 1 a disguised Medium problem.

---

## Slot 2 — Multi-step basic implementation

Target solve time: approximately **10–15 minutes**.

Typical skills may include:

* strings;
* arrays;
* frequency counting;
* HashMap/HashSet usage;
* simple transformations;
* fixed-length windows;
* simple prefix information;
* basic pattern matching;
* multiple dependent conditions;
* nested loops when constraints make them reasonable.

Characteristics:

* Requires more reasoning than Slot 1 but should usually have a straightforward implementation once understood.
* Do **not** require a sophisticated optimization insight merely because it is Slot 2.
* If an O(n²), O(n·m), or similar direct solution is intentionally acceptable, choose constraints that clearly make it acceptable.
* Alternatively, a simple O(n) map/window solution is fine if it is natural.
* Usually one main concept plus careful implementation.
* Avoid turning Slot 2 into a miniature Slot 4.

---

## Slot 3 — Implementation-heavy problem

Target solve time: approximately **15–25 minutes**.

This slot should primarily test **implementation ability**, not discovery of an obscure algorithm.

Good formats include:

* 2-D matrices;
* simulations;
* movement or state transitions;
* applying multiple ordered rules;
* repeated transformations;
* placement/collision logic;
* interval/state manipulation;
* processing a sequence of operations;
* coordinate or grid manipulation.

Characteristics:

* Several rules interact.
* Correctness requires careful bookkeeping.
* Edge cases and boundaries matter.
* A candidate may understand the approach immediately but still need significant time to implement it correctly.
* The intended solution may be relatively long compared with the other problems.
* Avoid requiring a major algorithmic trick on top of the implementation burden.
* Rectangular matrices and asymmetric boundary cases are preferred over examples that accidentally encourage square-only assumptions.
* Hidden tests should strongly distinguish correct state modeling from solutions that merely pass the examples.

The problem should feel like:

"I know roughly what to do, but I need to implement this carefully."

not:

"I need to know a specialized algorithm."

---

## Slot 4 — Algorithmic problem solving / optimization

Target solve time: approximately **20–30 minutes**.

The obvious or brute-force approach should be easy to identify but too slow at maximum constraints.

The candidate should need to discover a more efficient representation, invariant, lookup strategy, ordering, or feasibility test.

Rotate among broadly useful algorithmic families across generated assessments. Examples include:

* hash lookup / frequency maps;
* algebraic transformation followed by lookup;
* prefix sums;
* prefix-state compression;
* sorting plus scanning;
* sorting plus binary search;
* two pointers;
* sliding windows;
* greedy reasoning;
* binary search on a monotonic answer;
* monotonic stack or deque when natural;
* coordinate/value normalization.

Do not default to the same HashMap pair-counting problem every time.

The intended complexity should normally be approximately:

* O(n),
* O(n log n), or
* O(n log M),

while an obvious O(n²) or worse approach should fail the largest cases.

The efficient solution should be derivable from the problem statement and constraints without requiring niche competitive-programming knowledge.

The problem should feel like:

"My first solution is too slow; what repeated work or mathematical/state relationship can I exploit?"

# CROSS-ASSESSMENT DIFFICULTY BALANCE

The assessment should have a meaningful progression, but do not simply make each problem longer than the previous one.

Slots 3 and 4 must be difficult for different reasons:

* Slot 3: implementation complexity and correctness.
* Slot 4: algorithmic insight and complexity optimization.

It is acceptable for some candidates to find Slot 4 faster than Slot 3 after seeing the key insight.

Do not make Slot 3 merely a weaker version of Slot 4.

Do not make Slot 1 or Slot 2 depend on a trick that would cause a strong candidate to spend most of the assessment there.

---

# PROBLEM-WRITING STYLE

Use concise technical prose similar to professional coding-assessment questions.

Every problem description must clearly define:

1. inputs;
2. required output;
3. all transformation or matching rules;
4. ordering of operations where relevant;
5. indexing convention if relevant;
6. behavior at boundaries;
7. behavior for ties if relevant;
8. whether input may be modified if that matters.

Prefer concrete rules over narrative fluff.

A light scenario is allowed, but the scenario must not obscure the computational task.

Avoid unnecessarily long stories.

Examples should demonstrate the rules rather than merely repeat the final answer.

Use 0-based indexing unless there is a compelling reason not to.

Do not reveal the intended algorithm in:

* the title;
* the description;
* example explanations;
* constraints.

For example, do not title a problem `"Prefix Sum Counter"` or tell the candidate to "use a HashMap."

`generationMetadata` may identify the underlying skills and intended complexity for analysis purposes, but the actual problem statement must remain solution-neutral.

---

# CONSTRAINT DESIGN

Constraints must be deliberate.

For every problem, choose bounds such that:

* the intended solution comfortably fits within `executionTimeMs`;
* an approach that the problem is intended to permit will pass;
* an approach that the problem is specifically intended to rule out will meaningfully struggle or fail;
* integer overflow considerations are internally consistent with the return type.

Use `"long"` when the correct answer can exceed a 32-bit signed integer.

Do not declare huge constraints merely to make a problem look difficult.

Do not create a Slot 1 or Slot 2 problem where an otherwise natural direct implementation unexpectedly times out.

For Slot 4, explicitly ensure the maximum constraints make the obvious naive approach asymptotically unsuitable.

---

# TEST DESIGN

Tests are part of the assessment design, not an afterthought.

For each problem aim for:

### Visible

* 2–4 visible tests.

Visible tests should:

* cover the normal interpretation;
* include at least one useful nontrivial example;
* not expose every important edge case.

### Hidden

Aim for approximately **15–25 hidden tests total per problem**, rather than mechanically maximizing test count.

Include a balanced mixture of:

* ordinary correctness cases;
* minimum-size boundaries;
* maximum/minimum values where relevant;
* empty-like behavior when permitted by constraints;
* single-row/single-column behavior when permitted;
* duplicates;
* ties;
* negative values where permitted;
* repeated values;
* asymmetric cases;
* off-by-one boundaries;
* adversarial cases aimed at plausible incorrect implementations;
* performance-oriented cases where needed.

For Slot 3, hidden tests should specifically target:

* incorrect boundary handling;
* wrong operation order;
* square-matrix assumptions;
* incomplete state tracking;
* accidental mutation/order bugs;
* repeated or overlapping operations when applicable.

For Slot 4, hidden tests should specifically target:

* correct but too-slow naive approaches;
* duplicate handling;
* double counting;
* integer overflow;
* state collisions or normalization errors;
* failure to preserve the earliest/latest occurrence when that distinction matters.

Do not create enormous explicit JSON arrays solely to claim a "stress" test.

The judge executes only the concrete test cases in the JSON; declared constraints alone do not enforce time complexity. For Slot 4, include at least one concrete hidden performance case large enough to distinguish the intended solution from the naive approach while keeping the complete JSON below 2 MB. Choose a problem whose naive solution can be stressed within that import budget.

Prefer compact but adversarial test data where possible.

# REFERENCE SOLUTION QUALITY

Every Python reference solution must:

* be correct for all declared constraints;
* implement the intended efficient solution;
* be deterministic;
* avoid external packages;
* avoid filesystem, environment, network, process, or dynamic-code side effects such as `open`, `os`, `subprocess`, `socket`, `eval`, `exec`, or dynamic imports;
* avoid reading input or printing output;
* define exactly one callable `solution(...)` entry point;
* return a value matching the declared TypeSpec.

Reference code may define helper functions if needed.

For Slots 1–3, prefer readable solutions that directly implement the specification.

For Slot 4, the reference solution must use the intended efficient complexity rather than brute force.
