## SUPPORTED TYPES AND IDENTIFIERS

Supported TypeSpec values are only:

* `{"kind":"int"}`
* `{"kind":"long"}`
* `{"kind":"boolean"}`
* `{"kind":"string"}`
* recursively, `{"kind":"array","items":TypeSpec}`

Do not use tuples, objects, maps, sets, custom structures, nullable values, floating-point types, graphs, or tree nodes as values. Graphs and trees may be represented with supported arrays when the representation is clearly documented.

Every function and parameter name must be a portable Java/C++/Python identifier using ASCII letters, digits, and underscores, not starting with a digit or using a reserved word. Parameter names must be unique within each signature.

`int` values must fit signed 32-bit range. `long` values must be JSON safe integers. Every example and test argument list must exactly match the signature, and every output must match the return TypeSpec.

Execution limits must be integers within: `executionTimeMs` 1–10000, `compileTimeMs` 1–60000, and `outputLimitBytes` 1024–1048576.

Escape JSON string newlines, quotes, backslashes, and control characters correctly.

Every problem must set `validation.referenceLanguage` to `"python"` and provide a deterministic `validation.referenceSolution` defining `solution(...)` with parameters matching the signature.

## IMC SWE ASSESSMENT PROFILE

Bias difficulty slightly toward the harder side. The assessment is for software-engineering algorithmic coding, not trading or quantitative games. Do not include mental math, probability games, market making, finance trivia, or trading simulations.

Both questions must require meaningful reasoning, careful implementation, complexity analysis, and hidden-test robustness. The two questions should exercise different major skill families.

Difficulty should come primarily from modeling, optimization, state design, invariants, and implementation—not from obscure trivia or gratuitous combinations of unrelated algorithms.

Strongly favor varied combinations of:

* arrays, strings, hashing, sets, sorting, and binary search;
* prefix sums, intervals, greedy reasoning, heaps, and priority queues;
* stacks, monotonic structures, matrices, grids, and simulation;
* BFS, DFS, shortest paths, and augmented state;
* practical dynamic programming and memoization;
* preprocessing, offline queries, coordinate compression, and repeated-query optimization;
* trees represented by arrays, union-find, topological sorting, and custom data-structure behavior when natural.

Across repeated assessments, keep these important families recurring while varying story, objective, state representation, and optimization insight.

### Q1 — upper Medium to Medium-Hard

Target 40–50 minutes. Q1 must not be a warm-up Easy.

Require the candidate to understand the model, choose a representation, derive an efficient-enough solution, implement it carefully, and cover edge cases. Good combinations include sorting plus heaps, prefix sums plus hashing, intervals plus greedy reasoning, BFS/DFS, matrix reasoning, monotonic structures, or simulation with preprocessing.

### Q2 — Medium-Hard to Hard

Target 50–60 minutes. Prefer a problem with an understandable brute-force approach whose repeated work is ruled out by the constraints.

Q2 should usually require one central algorithmic insight plus whatever supporting techniques arise naturally. Combining multiple techniques is desirable when the problem genuinely requires them, but do not increase difficulty by stacking unrelated algorithms. Prefer depth of reasoning over algorithm-count complexity.

Suitable techniques include binary search on answer, augmented graph search, Dijkstra, multidimensional DP, greedy plus an ordered structure, offline processing, tree preprocessing, monotonic deque/stack, coordinate compression, sweep-line sorting, memoization, or repeated-query optimization.

Do not force an obscure algorithm merely to label the problem Hard. Avoid puzzle-like tricks with no transferable software-engineering value.

## COMPLEXITY AND CONSTRAINTS

Complexity must matter. Frequently make an obvious O(n²) or per-query rescanning solution inadequate, while ensuring the intended solution comfortably fits the execution limit.

Performance tests should be as large as is practical within the literal-JSON test format. Where the schema makes true maximum-size stress testing impractical, prefer compact adversarial cases and sufficiently large deterministic inputs that meaningfully distinguish inefficient implementations.

Do not create enormous literal arrays solely to force a timeout.

The stated constraints must still make the intended asymptotic complexity necessary even when the embedded test suite cannot literally represent every maximum-size case.

Every stated constraint must be consistent with the intended solution, runner timeout, input representation, and hidden stress cases. Do not use fake maximums that are never meaningfully tested.

Do not reveal the intended algorithm in the title, description, examples, or constraints. `generationMetadata` may identify skills and expected complexity.

If intermediate calculations may exceed 32-bit range, make that discoverable from realistic constraints, use the `long` TypeSpec when the result requires it, and include a meaningful large-value test. Keep all JSON integer values within the safe range and avoid accidental oracle overflow.

## PROBLEM AND TEST QUALITY

Use concise, precise technical prose. Explicitly define indexing, boundaries, operation order, ties, mutation, unreachable cases, and return behavior. Avoid ambiguity as a source of difficulty.

For each problem include 3–4 meaningful visible sample tests and approximately 12–18 hidden tests.

Prefer a smaller number of high-information tests over many redundant tests. Every hidden test should target a specific correctness, boundary, overflow, performance, or adversarial behavior.

Include ordinary behavior, minimum sizes, duplicates, all-equal values, increasing/decreasing patterns, boundaries, empty results where valid, overflow-sensitive cases, off-by-one traps, disconnected or unreachable states where relevant, multiple equivalent choices, and compact adversarial stress cases.

Hidden tests must meaningfully detect brute-force timeouts, incorrect greedy assumptions, incomplete graph/search state, overflow, indexing errors, mutation bugs, duplicate mishandling, and boundary mistakes. Avoid redundant cases and enormous literal arrays that bloat the response.

## REFERENCE SOLUTION REQUIREMENTS

Every Python reference solution must be correct, efficient, deterministic, use no external packages, read no input, print no output, and avoid filesystem, environment, network, subprocess, socket, dynamic import, `eval`, or `exec` behavior. Helper functions are allowed.

Before responding, execute every example and every visible and hidden test against its Python reference solution when tools are available. Correct all mismatches before returning JSON.
